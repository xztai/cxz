# Тестовые подписки и ЮKassa

Этап 4 использует один тестовый магазин платформы. Реальных выплат авторам,
комиссии и возвратов через интерфейс нет. Все суммы — целые копейки RUB, даты — UTC.

## Настройка

В локальном `.env` задайте обе переменные:

```dotenv
YOOKASSA_SHOP_ID=идентификатор_тестового_магазина
YOOKASSA_API_KEY=секретный_ключ_тестового_магазина
```

Если оплата не нужна, оставьте обе пустыми. Задание только одной переменной
останавливает запуск с понятной ошибкой конфигурации. Разрешены только ключи
тестового магазина (`test_…` или `secret_test_…`); подтверждение дополнительно
проверяет `test=true` у каждого платежа. Ключи доступны только Go API и worker,
не попадают во frontend, OpenAPI, журналы или образы.

В кабинете ЮKassa включите автоплатежи / сохранение способа оплаты для тестового
магазина, если нужен сценарий продления. Наличие галочки в etheyl не гарантирует
сохранения: автопродление включается окончательно только при подтверждённом
`payment_method.saved=true` и непустом ID сохранённого способа оплаты.

```sh
docker compose up --build --wait
# Проверка прав runtime-ролей после миграций:
docker compose exec -T postgres psql -U etheyl -d etheyl < scripts/check-db-roles.sql
```

Автор создаёт профиль, уровень от 1 ₽ и закрытый пост. Подписчик выбирает уровень
на странице автора → подтверждает цену и, при желании, автопродление → открывает
страницу оплаты ЮKassa → возвращается на страницу результата. Не вводите реальные
платёжные реквизиты в тестовый магазин. Тестовые данные и сценарии отказа приведены
в [документации ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).

## HTTPS и уведомления

Установите `APP_ORIGIN=https://ваш-домен` и `COOKIE_SECURE=true`, обеспечьте доступный
ЮKassa HTTPS reverse proxy с действительным сертификатом. Входящие уведомления
в кабинете тестового магазина направьте на:

```text
https://ваш-домен/api/v1/billing/yookassa/webhook
```

События: `payment.succeeded`, `payment.canceled`; `payment.waiting_for_capture`
обрабатывается как требующее проверки, поскольку etheyl создаёт одностадийные
платежи с `capture=true`. Локальный Compose опубликован только на loopback и сам
по себе не является внешним HTTPS endpoint; можно использовать HTTPS tunnel до
локального proxy, согласовав его origin с `APP_ORIGIN`. Не публикуйте worker,
PostgreSQL, MinIO и Mailpit. Настройка сертификатов и внешнего reverse proxy —
[operations.md](operations.md).

Webhook — отдельный server-to-server endpoint: он отклоняет Cookie и Origin,
не использует сессию пользователя и не доверяет данным события. Из события берётся
только ID, затем выполняется аутентифицированный GET к ЮKassa. Проверяются ID
магазина, `test`, сумма, RUB, ID внутренней попытки и соглашения в metadata,
а также уже закреплённый ID провайдера. Браузерные мутации по-прежнему требуют
точный Origin и CSRF-cookie/header, включая оформление и отмену подписки.

Worker сверяет известные незавершённые платежи примерно раз в 30 секунд, поэтому
пропущенный webhook или локальный запуск без внешнего HTTPS не блокирует результат.
Переход пользователя по `return_url` не выдаёт доступ; GET статуса ничего не меняет.

## Гарантии жизненного цикла

- `billing_agreements` хранит условия оплаты; `subscriptions` — только оплаченный
  доступ. До подтверждения успешного платежа записи доступа не создаются.
  На пару подписчик/автор приходится одно соглашение и один актуальный grant.
- Запрос и ключ идемпотентности сохраняются в `payments` до обращения к ЮKassa.
  Все повторы используют **тот же запрос и тот же ключ**. Worker забирает попытку
  через `FOR UPDATE SKIP LOCKED` и lease 30 секунд; падение процесса позволяет
  продолжить её после истечения lease. HTTP к провайдеру выполняется без открытой
  бизнес-транзакции. Порядок бизнес-блокировок: автор → соглашение → попытка.
- Сохранённый ID провайдера используется для GET вместо повторного POST.
  Если ответ на создание потерян и ID неизвестен, повторяется исходный POST с тем
  же ключом в пределах 23 часов от первой отправки. Затем попытка переходит в
  `review`: окно гарантированной идемпотентности ЮKassa — 24 часа, поэтому новый
  POST или новый платёж до ручной сверки запрещён.
- Успех атомарно фиксирует финальный статус, оплаченный период и grant; повторные
  и конкурирующие уведомления не продлевают доступ повторно. Терминальные статусы
  не заменяются запоздалыми ответами `pending`.
- Период — календарный месяц. 31 января → последний день февраля → 31 марта;
  используется сохранённый день расчёта. После длительной остановки worker
  не списывает деньги за несколько уже истёкших месяцев: новый период начинается
  с подтверждения очередной оплаты, если прежний период продления уже целиком прошёл.
- Без явного согласия нет сохранения способа оплаты и автоматических списаний.
  Цена фиксируется в соглашении; редактирование уровня не меняет текущую цену.
  Смена уровня отдельно подтверждает актуальную цену и применяется только после
  оплаты следующего периода, без пересчёта текущего.
- Отмена, архивирование текущего/запланированного уровня и блокировка аккаунта
  отключают будущие продления. Несланная задача отменяется перед отправкой.
  Списание, уже разрешённое worker до отмены, может завершиться позже: его результат
  обязательно сверяется, оплаченный доступ сохраняется. Разблокировка ничего
  автоматически не возобновляет.
- Отказ прекращает продление и в той же транзакции ставит одно зашифрованное письмо
  в outbox. Повторных автоматических попыток отклонённого списания нет. Оплаченный
  доступ сохраняется; после окончания пользователь может вручную выбрать уровень
  и создать новую оплату. Недоступность провайдера не считается отказом платежа.

## Неопределённый результат

В `/account/payments` попытка `review` отображается как «Уточняем результат».
Новая оплата для того же автора блокируется. Найдите попытку в БД, а платёж в кабинете
ЮKassa — по metadata `etheyl_payment_id`; не выводите `request_body`, ключи или способ
оплаты в журнал. После нахождения ID выполните проверку через провайдера:

```sh
docker compose exec api etheyl reconcile-payment --provider-id ID_ПЛАТЕЖА_ЮKASSA
```

Команда **не создаёт платежей**: только GET и штатная проверка всех реквизитов.
После команды проверьте статус соответствующей попытки в истории. При отсутствии
платежа у провайдера не снимайте блокировку SQL-командой без расследования: старый
платёж всё ещё может существовать. Возврат к исходному POST спустя 24 часа небезопасен.

Сбой SMTP не повторяет платёж. Повторить окончательно неотправленное письмо можно
через существующую `etheyl requeue-mail --id ID` (до окончания срока письма).

## Проверки

```sh
make generate
make lint
make test-integration
make test-restore
cd frontend
pnpm peers check
pnpm check:mcp
pnpm test:unit
pnpm check
pnpm build
pnpm test:e2e:billing
```

Интеграционные тесты используют изолированную PostgreSQL и fake ЮKassa, без внешних
ключей: успех открывает закрытый пост; проверяются неверные магазин/сумма/валюта/
metadata/test, поддельные и повторные уведомления, потеря ответа, перезапуск и
конкурирующие задачи, истечение окна идемпотентности, фиксированная цена, смена
уровня, отказ, письмо, отмена, архивирование, блокировка и длительная остановка.
Unit-тесты проверяют календарь и безопасный HTTP-клиент. Браузерная billing-группа
на desktop/mobile проверяет реальные регистрацию и страницы, явное согласие,
запрос цены, ошибку оплаты и пустые состояния; ответ оформления в этом тесте
подменяется, чтобы CI не обращался к внешнему магазину. Она не заменяет ручную
оплату на размещённой у ЮKassa странице. Каждая группа CI получает свежий Compose.
