# Эксплуатация и восстановление

Этот runbook дополняет локальный Compose. Публичный production ещё не развёрнут.
Ответственный за релиз и дежурство — сопровождающий репозитория; перед публичным
запуском он назначает конкретных людей и проверяет доступ к backup storage,
секретам, DNS, SMTP и мониторингу. Цели первого production: RPO не более 15 минут,
RTO не более 2 часов. Это цели, до проверки внешней инфраструктуры они не являются SLO.

## Роли и секреты

`make init` создаёт `.env` с правами 0600 и дописывает только отсутствующие настройки.
Существующие значения остаются прежними. `.env` не попадает в Git или build context.
`db-roles` под bootstrap-пользователем создаёт `etheyl_migrator`, `etheyl_api`,
`etheyl_worker`; затем migrate применяет SQL, `db-grants` выдаёт минимальные права.
API не может читать body outbox или выполнять DDL. Worker не читает email/хеши
паролей пользователей и не изменяет аккаунты. Проверка на отдельном стенде:

```sh
docker compose exec -T postgres psql -U etheyl -d etheyl < scripts/check-db-roles.sql
```

Bootstrap-пароль и пароль владельца схемы получают только одноразовые jobs и БД.
API/worker получают свои credentials и ключи outbox; migrator не получает ключи
outbox. В production хранить секреты в secret manager и выполнять bootstrap/grants
из отдельного deployment job, без постоянно доступного runtime bootstrap-секрета.
Не менять `POSTGRES_PASSWORD` существующего volume через один `.env`: обновление
пароля самой bootstrap-роли требует отдельного `ALTER ROLE`.

Outbox body зашифрован AES-256-GCM со случайным nonce. AAD связывает шифротекст
с адресатом, темой и digest токена. `OUTBOX_KEYS` — ключи в base64 через запятую,
активный первым; ключи хранить отдельно от дампов и ограничить доступ к их backup.
Для ротации сначала распространить `новый,старый` на API и worker, затем переключить
всех писателей, дождаться удаления старых писем (максимум 24 часа, плюс cleanup)
и убрать старый ключ. При rolling deploy старые workers сначала должны узнать новый
ключ как дополнительный; только затем писатели переключаются на него.
Ключи не печатать в логи или аргументы CLI. Потеря ключа делает старую очередь
нечитаемой: запросить новые письма, после чего удалить недействующие записи.

Миграция 00003 удаляет ожидающие plaintext-письма старого формата. После обновления
получатели таких писем должны запросить ссылку заново; уже доставленные ссылки
сохраняют прежний срок действия. Down также удаляет зашифрованные письма, поскольку
старый worker не умеет их читать. Не понижать версию worker отдельно от схемы.

## Доставка и диагностика

Liveness `/api/v1/health` проверяет процесс/БД и используется Compose. Отдельный
внутренний endpoint worker `GET /api/v1/mail/status` возвращает pending, failed,
oldestSeconds, heartbeat, lastPoll, lastSuccess (последний успешный SMTP Send в этом
процессе). Внешний proxy этот endpoint worker не публикует. Он возвращает 503 при
failed > 0, возрасте очереди > 300 с, отсутствии heartbeat/poll более 30 с или
отказе БД. В production опрашивать его каждые 15 с и уведомлять дежурного после
двух минут деградации; отдельно контролировать исчезновение самого endpoint.
Временный SMTP-сбой не должен перезапускать контейнер.

Worker делает максимум восемь попыток, затем выставляет failed_at/failure_code;
ошибка расшифровки сразу окончательная. Просроченные, заменённые, использованные
или заблокированные action-токены не отправляются. Cleanup раз в минуту удаляет
недействующие письма, включая dead letters; срок хранения body ограничен сроком
ссылки. После исправления SMTP/ключей повторить конкретное ещё актуальное письмо:

```sh
docker compose exec worker etheyl requeue-mail --id 123
```

Повтор проверяет актуальность токена и сбрасывает попытки. Если ссылка уже истекла,
нужно новое письмо через обычный пользовательский сценарий. SMTP остаётся at-least-once:
авария после Send до commit может дать повторную доставку одноразовой ссылки.

API выдаёт `X-Request-ID` и журналирует метод, шаблон маршрута, статус, длительность;
внутренние сбои — безопасную категорию и SQLSTATE. Panic trace содержит имена функций,
файлы и строки без значений аргументов и panic. Поиск инцидента вести по request ID.
Не включать raw DB/SMTP errors, SQL-параметры, query strings, body, cookie или ссылки
в журналы. Метрики очереди и состояние failed не содержат адресов или токенов.

HTTP deadline по умолчанию 5 с (`REQUEST_TIMEOUT`, 100 мс–15 с); SQL statement_timeout
4 с, lock_timeout 2 с. У worker отдельный deadline операции 20 с/SMTP 15 с. Роли
имеют серверные timeout, мигратор — lock 5 с/statement 30 с и общий deadline 5 мин.
Не повторять автоматически мутации с неизвестным результатом commit. Проверять
фактическое состояние сессии/аккаунта и предлагать пользователю явный следующий шаг.

## Релиз и миграции

Перед релизом: зелёные CI/security, backup и успешный restore drill на отдельной БД,
проверенная совместимость схемы со старым/новым приложением. Один migration job на
окружение; advisory session lock goose сериализует случайный параллельный запуск.
При истечении lock timeout остановить релиз и выяснить блокирующую транзакцию;
не повторять DDL в цикле. Приложение и schema owner используют разные credentials.

Историческая 00002 уже используется локальными volumes, её SQL не переписывается.
Она выполняет полный backfill nickname под DDL-блокировкой: для существующей
большой таблицы назначить окно обслуживания, сначала измерить время на восстановленной
копии и остановить API/worker на время миграции. Если 30 с недостаточно, выделить
контролируемый migration job с согласованным timeout после измерения, а не снимать
ограничение у runtime. Down/Up 00002 теряет выбранные nickname и назначает user-ID;
возврат выбранных значений возможен только восстановлением backup.

Следующие backfill делать expand/contract: добавить nullable колонку короткой
миграцией, развернуть совместимый код с двойной записью, заполнить по ID пакетами
с отдельными commit, затем создать UNIQUE INDEX CONCURRENTLY в нетранзакционной
миграции, добавить CHECK NOT VALID/VALIDATE и коротко включить NOT NULL/constraint.
При ошибке concurrent index проверить/удалить INVALID index перед повтором.
Удаление старой колонки выносить в следующий релиз после срока обратной совместимости.

Откат приложения: вернуть предыдущий digest только если он совместим со схемой.
Откат данных: остановить запись, восстановить проверенный backup/PITR в новую БД,
проверить целостность/права/авторизацию и переключить DATABASE_URL. Не делать `goose down`
в production вместо восстановления данных. Исходную БД сохранять для расследования.

## Backup / restore

Для production: ежедневный pg_dump custom, WAL/PITR для RPO 15 мин, шифрованная копия
в отдельном аккаунте/хранилище с immutable retention 30 дней и контролем свежести
последнего WAL. До запуска настроить реальное расписание и алерт > 15 мин отставания.
Backup ключей outbox хранить отдельно; SQL-дамп содержит хеши паролей, персональные
данные и шифротексты и тоже требует ограниченного доступа. Volume не является backup.
Пример ручного локального dump с остановкой писателей для согласованного drill:

```sh
umask 077
docker compose stop api worker
docker compose exec -T postgres pg_dump -U etheyl -d etheyl -Fc > etheyl.backup
# Сразу запустить сервисы после завершённого dump.
docker compose start api worker
```

Восстановление выполнять в НОВУЮ пустую БД на той же major-версии PostgreSQL:
создать роли через bootstrap, `pg_restore --no-owner --no-acl --exit-on-error`,
передать ownership таблиц/identity sequences migrator через bootstrap и применить
grants. Проверить goose version, количество/контрольные суммы таблиц, уникальность
nickname, вход, `/me`, отзыв сессий после reset и тестовую доставку. Восстановленные
сессии при инциденте утечки отозвать, очистив sessions; старые action_tokens/outbox
очистить и запрашивать новые ссылки. Зафиксировать длительность и достигнутый RPO.

`make test-restore` реализует реальный pg_dump/pg_restore в отдельную случайную БД
в контейнере `etheyl-tests`, сравнивает количество и digest всех шести таблиц и удаляет
только созданную им БД. Основной etheyl volume не используется. Перед выполнением
завершить `make test-integration`, чтобы дамп не пересекался с TRUNCATE тестов.
В CI drill выполняется после Go-тестов. Ежемесячно повторять на production-backup
в изолированном окружении без исходящего SMTP.

MinIO пока не содержит бизнес-данных. До этапа медиа включить versioning/репликацию
в отдельный storage account, согласовать SQL/object snapshot и проверить восстановление
объектов по checksum. Отдельно сохранять конфигурацию и IAM, ключи — в secret manager.

## Production-параметры и данные

Внешний ingress должен обслуживать HTTPS с продлением сертификатов, передавать
точный APP_ORIGIN=https://домен и перезаписывать X-Real-IP; `COOKIE_SECURE=true`,
`TRUST_PROXY=true` только за этим ingress. Убрать Mailpit и его порт, настроить внешний
SMTP_HOST/PORT/FROM и credentials, `SMTP_INSECURE=false`. Проверить доставку,
SPF/DKIM/DMARC и recovery, не публиковать PostgreSQL/MinIO/worker наружу. Локальный
compose остаётся HTTP-окружением разработки и сам по себе этим требованиям не отвечает.

Политика до публичного запуска: неподтверждённые неадминистративные аккаунты хранить
30 дней, затем удалять пакетной задачей с аудитом количества, каскадным удалением
сессий/токенов и очисткой outbox. Сейчас автоматическое удаление аккаунтов не включено,
чтобы не менять продуктовую политику локального MVP. Для production job и уведомление
в политике конфиденциальности — обязательные пункты release checklist. Удаление
подтверждённого аккаунта пока не реализовано; реальные аккаунты не запускать до
реализации процедуры запросов владельцев и согласования retention с применимыми правилами.
Ответ 409 занятого email — сознательный продуктовый компромисс приватности.

Security workflow запускает govulncheck 1.9.0, pnpm audit, Gitleaks 8.30.1 и Grype
0.121.3 по PR/push и еженедельно. Бинарные релизы фиксированы SHA-256 в installer;
Actions — SHA, отчёты зависимостей/образов — artifacts на 30 дней. High/Critical блокируют
релиз; ответственный сопровождающий разбирает их за 1 рабочий день, обновляет с тестами
до следующего релиза (Critical — в день разбора). Low/Medium — разбор еженедельно.
Исключения только с причиной, владельцем и датой пересмотра; auto-fix не включён.

## Advisory при проверке исправлений

Grype обнаружил CVE-2026-4738 у zlib 1.3.2-r1 в прежнем backend image. В Dockerfile
backend/frontend/MinIO закреплён zlib=1.4-r0 — исправление для Alpine 3.24 указано
в [официальном трекере Alpine](https://security.alpinelinux.org/vuln/CVE-2026-4738).
Результат повторных image scans указан в дополнении REVIEW.md.

`pnpm audit` сообщает один Low: [GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4)
у deepmerge, исправленной версии на дату проверки нет. Advisory не скрывается;
сопровождающий проверяет обновление еженедельно (первый пересмотр 19 ноября 2026).
Не передавать недоверенные объекты в операции merge; это не доказательство эксплуатации
через существующие формы etheyl. High/Critical-пропусков в CI не добавлено.

MinIO RELEASE.2025-10-15T17-29-55Z содержит дополнительные High/Critical advisory
в Go-зависимостях (grpc, x/net, x/crypto, thrift, amqp091-go и др.). Это остаётся
[последним официальным релизом upstream](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z).
По решению владельца MinIO сохранён, его security job остаётся блокирующим; bypass
и suppressions не добавлены. До отдельного обновления/замены и проверки совместимости
хранилище не подключать к реальным данным. Это дополнительная находка нового сканера,
а не устранённая проблема. zlib=1.4-r0 применён и к MinIO, но не исправляет его Go-модули.
В frontend runtime удалён ненужный npm с его уязвимыми зависимостями; Node и зависимости
приложения сохранены, сборка продолжает использовать npm/pnpm в build stage.
