# Этап 1 — реализация и проверка

Реализованы разделение frontend/backend, SvelteKit с shadcn-svelte и общей темой, REST API `/api/v1`, контракт OpenAPI и типизированный клиент, PostgreSQL/sqlc/goose, CLI администратора, очередь писем и локальная инфраструктура Compose.

Авторизация включает регистрацию по email и уникальному никнейму, повторную отправку подтверждения, подтверждение email с автоматическим входом, вход по email, выход, восстановление и сброс пароля. Никнейм — 3–30 символов ASCII: латиница, цифры, `_` и `-`; без точек, с уникальностью без учёта регистра. Перед подтверждением сервер возвращает адрес по токену без его погашения. Занятый email или никнейм при регистрации сразу возвращает 409; исходный аккаунт, ссылка и очередь писем не меняются. Кнопка повторной отправки есть только в карточке «Проверьте почту». Пароли хешируются Argon2id, сессии находятся в БД, cookies HttpOnly. CSRF проверяется и для анонимных действий; лимиты общие для экземпляров API. Установка текущего пароля возвращает 422 и сохраняет ссылку и сессии; успешная смена пароля отзывает все сессии.

Go-интеграционные тесты используют настоящую БД и проверяют: нормализацию email, отклонение повторной регистрации без нового письма и изменения пароля/имени/токена, запрет назначения администратора при регистрации, получение адреса по токену без авторизации, автоматический вход после подтверждения, замену и одноразовость ссылок, истечение токена и сессии, безопасные cookies, CSRF/Origin, ошибки JSON, общие лимиты, отзыв сессий после сброса, выход, права администратора, конкурентное подтверждение с созданием ровно одной сессии и выборку писем двумя worker с блокировками. При отказе SMTP проверяются счётчик попыток и отложенная отправка.

Дополнительно проверены запрет точек, кириллицы, пробелов и URL-разделителей в никнеймах, нормализация регистра, конкурентная регистрация одного никнейма с разными email (создаются только один аккаунт и одно письмо), обратимость миграции никнеймов, отказ сброса на текущий пароль с успешной повторной попыткой по той же ссылке. Браузерные сценарии проверяют, что после входа неподтверждённого аккаунта открывается карточка «Проверьте почту», повторная отправка работает в этой карточке, а при повторной регистрации уже подтверждённого аккаунта предложения отправить письмо нет.

Playwright выполняется на production-приложении в Compose с PostgreSQL, worker и Mailpit. Проекты: desktop 1440×1000 и mobile 390×844. Сценарии покрывают регистрацию → письмо → отказ повторной регистрации → показ email из исходной ссылки → подтверждение и автоматический вход → выход → ошибочный вход → успешный вход → перезагрузку с серверной сессией → переключение кабинетов → восстановление → отзыв старой сессии → вход новым паролем → запрет кабинета администратора обычному пользователю → выход. Дополнительно проверяются клавиатура, выравнивание футеров карточек, отсутствие горизонтального переполнения, пустая и недействительная ссылка, включая смену fragment на уже открытой странице. Недействительная ссылка обнаруживается до нажатия кнопки подтверждения. Проверяется отсутствие ошибок JavaScript и нарушений CSP в основном сценарии.

Проверки выполнены локально. GitHub workflow настроен на push/PR; удалённый запуск GitHub Actions в рамках реализации не инициировался. Его команды проверены локально, синтаксис workflow проверен actionlint.

## Настройка агента

`pnpx sv add ai-tools` выполнен из `frontend/`. Сгенерированный AGENTS.md сохранён; инструкции дополнены. Официальные skills находятся в `frontend/.agents/skills`; локальный MCP прописан в `frontend/.codex/config.toml`. Codex следует запускать из `frontend/` в доверенном checkout; текущей сессии клиента может понадобиться перезапуск для обнаружения нового MCP.

## Границы этапа

Кабинет содержит состояние аккаунта и доступные режимы автора/подписчика. Кабинет администратора проверяет права; модерация будет на этапе 6. Каталог, профили, загрузки, публикации и платежи ещё не входят в реализованный этап. MinIO уже работает с постоянным volume в закрытой сети; его консоль отключена, работа приложения с объектами добавляется на этапе 2. HTTPS и внешний SMTP предусмотрены следующими этапами; текущий Compose локальный.
